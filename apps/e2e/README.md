# @vrp/e2e — browser end-to-end suite

Playwright (Chromium) tests that drive the **built** web app, API and worker the way a
customer, a provider and an administrator would, against the local PostgreSQL, Mailpit and
MinIO containers and the deterministic fake payment gateway. Nothing here is mocked except the
third-party map tiles (see below).

## Prerequisites

- Docker services up: `pnpm db:setup` from the repo root (PostgreSQL + PostGIS on 5432, Mailpit on
  1025/8025, MinIO on 9000) and the seed gazetteer loaded (`pnpm db:seed`; the suite searches for
  the seed place _Mirissa_).
- A repo-root `.env` (copy `.env.example`); the suite reads `DATABASE_URL`, `PGBOSS_SCHEMA` and the
  SMTP / storage settings from it and overrides the rest (see `fixtures/env.ts`).
- The Docker CLI on the PATH: one scenario moves a payment deadline into the past with
  `docker exec vehicle-rental-db psql …` (container name via `E2E_DB_CONTAINER`).
- Built artefacts: `pnpm build` from the repo root (the config starts `apps/api/dist/main.js`,
  `apps/api/dist/worker.js` and `next start`).
- A Chromium-based browser. By default the suite drives the installed **Google Chrome**
  (`channel: 'chrome'`), so nothing has to be downloaded. `PLAYWRIGHT_CHANNEL=msedge` uses
  Microsoft Edge; an empty `PLAYWRIGHT_CHANNEL=` selects Playwright's bundled Chromium, which
  must be installed first with `pnpm --filter @vrp/e2e install:browsers` (recommended for CI, where
  the browser version is then pinned to the Playwright version).
- Ports 3000 (web), 4000 (API) and 4710 (worker health wrapper) must be free: the servers are
  started by Playwright itself with `reuseExistingServer: false`, so a running `pnpm dev` must be
  stopped first.

## Running

```bash
pnpm build                              # whenever apps/api, apps/web or packages/* changed
pnpm e2e                                # = pnpm --filter @vrp/e2e test (all specs, headless)
pnpm --filter @vrp/e2e test:headed      # watch the browser
pnpm --filter @vrp/e2e test tests/provider.spec.ts   # one file
pnpm --filter @vrp/e2e exec playwright show-report  # HTML report of the last run
```

The run starts the API (`NODE_ENV=development`, `PAYMENT_GATEWAY=fake`, `ADMIN_MFA_REQUIRED=true`,
raised per-IP rate limits, one-hour access tokens), the worker (through
`scripts/run-worker.mjs`, which adds the health endpoint Playwright waits for) and the web app
(`next start` on port 3000), runs the `setup` project (one super admin with an authenticator and
one approved provider, saved to `.world/world.json`) and then the spec files, three in parallel.
Every spec creates its own vehicle, customers and — where it logs an admin in — its own admin
account, so booking windows and authenticator codes never collide. All servers are stopped at the
end. Results: `playwright-report/` (HTML), `test-results/results.json`, `test-results/a11y-summary.json`.

`pnpm test` at the repo root deliberately excludes this package (`turbo run test --filter=!@vrp/e2e`):
the suite needs the built servers and Docker, and takes several minutes.

## What is covered

| Spec                          | Scenario                                                                                                                                                                                                                                                                                      |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `customer-happy-path.spec.ts` | home → search (Mirissa, dates, price filter) → vehicle page quote → login mid-flow → request → provider accepts (API) → pay through the fake gateway → payment status → contact reveal → handover (API) → review in the UI → provider reply (API) on the public page                          |
| `provider.spec.ts`            | provider UI: inbox, accept, customer contact after the advance (fake gateway via API), pickup and return records, review reply, listing page, documents page                                                                                                                                  |
| `admin.spec.ts`               | two-step login with a TOTP code generated by the fixture, every console page renders without console errors, an admin without a verified factor is redirected to `/account/security?reason=mfa`                                                                                               |
| `failures.spec.ts`            | stale quote (price changed), stale version (accept twice), dates taken by an accepted request, contact locked before confirmation, failed / cancelled / successful payments, review locked after the provider reply, protected scooter category, elapsed payment window expired by the worker |
| `accessibility.spec.ts`       | axe-core on home, search, vehicle, booking form, booking detail, provider booking detail, payment status, admin overview — `serious` / `critical` violations fail, the rest are attached and summarised                                                                                       |

Every page opened through the `page` fixture (`fixtures/test.ts`) is watched for `console.error`
output, uncaught exceptions and Content-Security-Policy refusals (`Refused to … Content Security
Policy`); any of them fails the test and the full list is attached to the report. Chromium also
logs `Failed to load resource` for API responses with 4xx statuses the application handles itself
(the 401 of the silent session refresh for anonymous visitors, the 403 / 409 refusals a failure
scenario provokes); those are recorded as `expectedApiRefusals` in the attachment but do not fail.

## Known defects the suite documents (not fixed here)

The suite cannot change `apps/web`, so findings are allow-listed with a precise match and
reported as `knownIssues` / `known` instead of failing (remove the entries once fixed):

- `KNOWN_CONSOLE_ISSUES` in `fixtures/test.ts` is empty. The MapLibre worker failure
  (`Error: Worker failed to load …`) was fixed on 2026-10-18 (risk register O12): the bundled
  worker could not resolve its hashed `./maplibre-gl-shared.mjs` import; the worker is now served
  from `/maplibre/`. `the pickup-area map on the public vehicle page renders` asserts the map and
  `… degrades to a notice when the tile host is unreachable` asserts the fallback.
- Fixed on 2026-10-18 after the first runs surfaced them (entries removed, tests now assert the
  working behaviour): the fake gateway's 303 back to the web app was refused by the API's helmet
  default `form-action 'self'` (the API now adds the `WEB_APP_URL` origin whenever it serves its
  development HTML pages); `GET /admin/system/worker` answered 500 while the worker was running
  (raw pg-boss rows carry string timestamps; the service now coerces them and treats a missing
  pg-boss schema as "down"); the web app shipped no favicon (`src/app/icon.svg`).
- `KNOWN_VIOLATIONS` in `tests/accessibility.spec.ts` is empty: the four `serious` axe findings
  of the first runs (destructive badge and alert text contrast, the map fallback notice contrast,
  the header account link's `label-content-name-mismatch`) were fixed in `apps/web` by darkening the
  `--destructive` and `--muted-foreground` tokens to WCAG AA ratios and making the link's
  `aria-label` start with the visible name. Any serious or critical violation now fails the test.

## Fixtures

- `fixtures/api.ts` — fetch wrapper for the API (`client: 'mobile'` logins, bearer tokens only).
- `fixtures/mailpit.ts` — reads verification links from Mailpit (`GET /api/v1/search`, `/message/{id}`).
- `fixtures/totp.ts` — RFC 6238 TOTP on `node:crypto`; `freshTotpCode` never hands out a step the
  server has already accepted for that secret.
- `fixtures/accounts.ts` — register + verify + login, `pnpm admin:grant` (child process from the
  repo root), authenticator enrolment (`/auth/mfa/enrol/start|confirm`).
- `fixtures/provider.ts` — provider application → admin approval → location → listing with the three
  committed JPEGs in `fixtures/assets/` → submit → admin approval.
- `fixtures/bookings.ts` — quotes, requests, provider transitions, fake-gateway payment outcomes,
  reviews and replies through the API; `rentalWindow(n)` builds `[start, end)` windows in Colombo days.
- `fixtures/db.ts` — `psql` inside the database container (only to move a payment deadline).

## Map tiles

The MapLibre style URL (`tiles.openfreemap.org`) is answered locally with an empty style so runs are
deterministic and offline-safe; the CSP must still allow the origin for the request to be made.
Set `E2E_REAL_MAP=1` to load the real tiles.
