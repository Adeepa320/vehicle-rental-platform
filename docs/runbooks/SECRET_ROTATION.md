# Runbook: secret rotation

**Status:** v0.1 (2026-10-17), Phase 10. Audience: the on-call engineer; the founder approves rotations that affect payments.
**Rules:** secrets live only in the deployment environment (Railway variables, sealed where possible) and in the operator's password manager; never in the repository, never in logs, never in this document. This runbook names variables, never values. Every rotation is recorded in section 12 (date, variable, reason, who; no values). Production does not exist yet: every vendor-side step is **EXTERNAL GATE — NOT EXECUTED**.
**Source of the variable list:** `apps/api/src/config/env.schema.ts` (names only). Production refuses the documented development values (`minioadmin`, the development encryption key, the fake gateway) and requires `JWT_PRIVATE_KEY` / `JWT_PUBLIC_KEY`, `BOOKING_QUOTE_SECRET`, `APP_DATA_ENCRYPTION_KEY`, `PAYHERE_MERCHANT_ID` / `PAYHERE_MERCHANT_SECRET` / `PAYHERE_NOTIFY_URL` and a non-memory e-mail and storage provider.
**Related:** [INCIDENT_RESPONSE.md](INCIDENT_RESPONSE.md), [DISASTER_RECOVERY.md](DISASTER_RECOVERY.md) §6 (lost encryption key), [PAYHERE_GO_LIVE.md](PAYHERE_GO_LIVE.md), docs/SECURITY_AND_PRIVACY.md §9.

## 1. When to rotate

| Trigger                                                                                                    | Scope                                                                                                                                                                                                                                     | Urgency                                |
| ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| Suspected or confirmed exposure (leak in a log, a laptop lost, a departing team member, a vendor incident) | The exposed secret and everything it could unlock                                                                                                                                                                                         | Immediately (SEV1 if payments or data) |
| A person with access leaves                                                                                | Every secret they could read: Railway variables, vendor dashboards, the password manager                                                                                                                                                  | Same day                               |
| Vendor requires or recommends it                                                                           | That vendor's credential                                                                                                                                                                                                                  | As scheduled                           |
| Routine                                                                                                    | `JWT_*`, `BOOKING_QUOTE_SECRET`, `STORAGE_*`, `SMTP_PASS`, `PAYHERE_APP_*`: yearly. `APP_DATA_ENCRYPTION_KEY`, `DATABASE_URL`, `PAYHERE_MERCHANT_SECRET`: only on exposure or departure (each has a user-visible or payment-visible cost) | Calendar                               |

## 2. General procedure

1. **Plan**: name the variable, read its row below (blast radius, overlap, order), pick a low-traffic window for payment and sign-in secrets (Colombo night), tell the founder.
2. **Generate** the new value with the tool named in the row; store it in the password manager first.
3. **Stage**: set the new value (and any `_PREVIOUS` overlap variable) in Railway for **both** the API and the worker services where the row says so; use sealed variables for everything in this runbook.
4. **Deploy** in the order the row gives; watch `GET /api/v1/ready`, the logs and the admin queues.
5. **Validate** with the row's checks.
6. **Retire** the old value at the vendor (revoke the key, delete the token) only after validation, and remove `_PREVIOUS` variables when the overlap window ends.
7. **Record** in section 12. Never paste values.

Rollback for any row: set the previous value back in Railway and redeploy; the rows note where rollback has side effects.

## 3. `JWT_PRIVATE_KEY` / `JWT_PUBLIC_KEY` (access-token signing, EdDSA)

| Item         | Detail                                                                                                                                                                                                                                                                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Blast radius | Anyone holding the private key can mint access tokens for any user and role for `ACCESS_TOKEN_TTL_SECONDS` (900 s) at a time. The MFA challenge token is signed with the same key (audience `vrp:mfa`)                                                                                                                  |
| Generate     | `pnpm --filter @vrp/api keys:generate` prints a new Ed25519 pair; copy both values to the password manager                                                                                                                                                                                                              |
| Overlap      | None today: a single key pair is loaded; there is no `kid`-based dual verification (planned later). Rotation therefore invalidates every outstanding access token at once                                                                                                                                               |
| Order        | Set both variables on the API service (the worker does not verify tokens); redeploy the API                                                                                                                                                                                                                             |
| User impact  | Signed-in users get `401` on their next API call and the web client silently refreshes with the HttpOnly refresh cookie (refresh tokens are opaque database records, unaffected by the key change). A user mid-way through an MFA challenge must sign in again. Mobile clients (none yet) would refresh in the same way |
| Validate     | Sign in, call `GET /users/me`, open `/admin` with an admin account (MFA challenge still works), `GET /api/v1/ready` green                                                                                                                                                                                               |
| Rollback     | Restore the previous pair and redeploy; tokens issued in between become invalid (same refresh behaviour)                                                                                                                                                                                                                |

## 4. `APP_DATA_ENCRYPTION_KEY` and `APP_DATA_ENCRYPTION_KEY_PREVIOUS` (AES-256-GCM data key)

| Item             | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What it protects | Today only `user_mfa.secret_ciphertext` (admin TOTP secrets). Envelopes are `v1.<keyId>.<nonce>.<tag>.<ciphertext>`; `keyId` is the first eight hex characters of SHA-256(key), so the application knows which key a row was written with (`apps/api/src/common/crypto/data-encryption.ts`)                                                                                                                                                                                                                                                                                                                   |
| Blast radius     | With the key and database access an attacker can recover admin TOTP secrets and pass the second factor. Without database access the key alone is useless; without the key the ciphertexts are unrecoverable                                                                                                                                                                                                                                                                                                                                                                                                   |
| Generate         | 32 random bytes, base64: `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"`. The documented development key is refused in production                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Overlap          | Built in: set `APP_DATA_ENCRYPTION_KEY_PREVIOUS` to the old key and `APP_DATA_ENCRYPTION_KEY` to the new key. The previous key **decrypts only**; every new write uses the current key. The two values must differ (the env schema refuses equal values)                                                                                                                                                                                                                                                                                                                                                      |
| Order            | 1. Set both variables on the API (the worker does not touch MFA). 2. Redeploy. 3. Re-encrypt existing rows: there is no re-encryption command yet; each admin either disables and re-enrols the factor (`POST /auth/mfa/disable`, then `/auth/mfa/enrol/start` and `/auth/mfa/enrol/confirm`, which also regenerates recovery codes), or engineering adds a reviewed re-encrypt script that reads with the previous key and writes with the current one. 4. Confirm with `pnpm admin:mfa-report --strict` that every admin has a confirmed factor. 5. Remove `APP_DATA_ENCRYPTION_KEY_PREVIOUS` and redeploy. |
| Validate         | Each admin completes an MFA challenge after the final deploy; `admin:mfa-report --json` shows `missing: 0`; the API log has no `no key for id` decryption errors                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Rollback         | Before step 5: swap the two variables back (current ← previous) and redeploy; rows already re-encrypted with the new key remain readable only while that key is present in either variable. After step 5: there is no rollback; a lost key means every admin re-enrols via `pnpm admin:mfa-reset` (DISASTER_RECOVERY.md §6)                                                                                                                                                                                                                                                                                   |

## 5. `PAYHERE_MERCHANT_SECRET` (checkout hash and notification signature)

| Item         | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Facts        | The Merchant ID is per account; the **Merchant Secret is per registered domain or app** in the PayHere Merchant Portal (Integration section). Checkout `hash` and notification `md5sig` are both computed with it (verified 2026-10-17)                                                                                                                                                                                                                                                                                                                                   |
| Blast radius | Anyone with the secret can forge a successful notification for any `order_id` and amount they know, which would confirm a booking without payment. The API protects against replay and amount mismatch but not against a correctly signed forgery. Treat exposure as SEV1                                                                                                                                                                                                                                                                                                 |
| Generate     | In the Merchant Portal: regenerate or create a new Integration record for the production domain (EXTERNAL GATE — NOT EXECUTED). Approval of a new domain can take up to 24 hours                                                                                                                                                                                                                                                                                                                                                                                          |
| Overlap      | **None on PayHere's side and none in the API** (one secret is loaded). Any notification PayHere sends for a payment started under the old secret, after the API has switched to the new one, fails verification and is recorded as `signature_valid = false`, never applied                                                                                                                                                                                                                                                                                               |
| Order        | 1. Pick a window with no open payment attempts if possible (watch `/admin/payments` and `GET /admin/bookings?status=accepted`). 2. Regenerate at PayHere. 3. Set `PAYHERE_MERCHANT_SECRET` on the API service (the worker does not use it) and redeploy. 4. Immediately reconcile every payment attempt that was pending during the window: `POST /admin/payments/{id}/reconcile` (needs Merchant API credentials) or the portal; a payment that PayHere shows as received but the API shows as pending is handled per OPERATIONS_RUNBOOK.md §4 (never confirmed by hand) |
| Validate     | A sandbox or small live test payment confirms a booking; `payment_events` shows `signature_valid = true`; no `Payment notification rejected` lines for new payments                                                                                                                                                                                                                                                                                                                                                                                                       |
| Rollback     | Set the old secret back **only if PayHere still accepts it** (a regenerated secret usually invalidates the old one); otherwise fix forward and reconcile                                                                                                                                                                                                                                                                                                                                                                                                                  |

## 6. `PAYHERE_APP_ID` / `PAYHERE_APP_SECRET` (Merchant API: Retrieval and Refund)

| Item         | Detail                                                                                                                                                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Blast radius | Read payment status by `order_id` and issue refunds for payments of this merchant, from allow-listed domains and (live) allow-listed IPs. Exposure enables unauthorised refunds; treat as SEV1 for money                                                            |
| Generate     | Merchant Portal → Settings → API Keys → Create API Key (name, allowed domains, "Automated Charging API" permission) → View Credentials. Live use additionally requires PayHere to allow-list the server IPs by e-mail to support@payhere.lk (PAYHERE_GO_LIVE.md §5) |
| Overlap      | Create the new key before deleting the old one; both work until deletion                                                                                                                                                                                            |
| Order        | Create new key → set both variables on the API → redeploy → run `POST /admin/payments/{id}/reconcile` on any payment → delete the old key in the portal                                                                                                             |
| Validate     | Reconcile returns gateway data instead of `503 not configured`; `payment_events` shows a reconcile row                                                                                                                                                              |
| Rollback     | Set the old pair back if it still exists                                                                                                                                                                                                                            |
| Note         | When these variables are unset the gateway's `canRefund` is false: admins record manual refunds only. That is an acceptable degraded state                                                                                                                          |

## 7. `DATABASE_URL` (database credentials)

| Item         | Detail                                                                                                                                                                                                                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Blast radius | Full read and write access to every table; everything in DATA_RETENTION.md §3                                                                                                                                                                                                                |
| Generate     | At the database vendor (Neon or Supabase; EXTERNAL GATE — NOT EXECUTED): create a new role with the same privileges, or reset the password of the application role. Prefer a new role so both work during the switch                                                                         |
| Overlap      | Two roles valid at once                                                                                                                                                                                                                                                                      |
| Order        | Set the new URL on the **worker and the API** (both connect; pg-boss uses the same URL) → redeploy both → confirm `GET /api/v1/ready` `database: up` and jobs flowing → drop or disable the old role at the vendor. Also rotate any read-only role used for dumps (BACKUP_AND_RESTORE.md §3) |
| Validate     | `/ready` green; a booking request creates `booking_events`; an e-mail job completes                                                                                                                                                                                                          |
| Rollback     | Set the old URL back while the old role still exists                                                                                                                                                                                                                                         |
| Note         | The `/ready` failure messages are fixed generic strings (no host, address, port or connection string; the cause is logged server-side with URLs redacted); logs never print `DATABASE_URL`. Keep it that way                                                                                 |

## 8. `STORAGE_ACCESS_KEY` / `STORAGE_SECRET_KEY` (S3 API credentials for R2)

| Item         | Detail                                                                                                                                                                                                                                         |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Blast radius | Read, write and delete on `vrp-private` (documents, photo originals) and `vrp-public`. Exposure is a potential personal-data breach (DATA_BREACH_RESPONSE.md)                                                                                  |
| Generate     | Cloudflare dashboard → R2 → API tokens: create a token scoped to the two buckets with object read and write only (no bucket create or delete in production; `STORAGE_AUTO_CREATE_BUCKETS` is off in production) (EXTERNAL GATE — NOT EXECUTED) |
| Overlap      | Two tokens valid at once                                                                                                                                                                                                                       |
| Order        | Create new token → set both variables on the API (the worker does not touch storage today) → redeploy → upload a test photo on a staging listing and stream a document as admin → revoke the old token                                         |
| Validate     | Photo upload returns variants; `GET /admin/documents/{id}/content` streams; no `AccessDenied` in logs                                                                                                                                          |
| Rollback     | Set the old pair back while the old token exists                                                                                                                                                                                               |

## 9. `SMTP_USER` / `SMTP_PASS` (Resend SMTP relay)

| Item         | Detail                                                                                                                                                                                                    |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Facts        | Resend SMTP: host `smtp.resend.com`, username `resend`, password = an API key; TLS on 465 or STARTTLS on 587 (`SMTP_SECURE`, `SMTP_REQUIRE_TLS`) (verified 2026-10-17)                                    |
| Blast radius | Send e-mail from the platform's domain (phishing against our users); read nothing                                                                                                                         |
| Generate     | Resend dashboard → API keys → create a sending-only key (EXTERNAL GATE — NOT EXECUTED)                                                                                                                    |
| Overlap      | Two keys valid at once                                                                                                                                                                                    |
| Order        | Create new key → set `SMTP_PASS` (and `SMTP_USER` if it changes) on the **worker** (the API only enqueues) → redeploy the worker → trigger a password-reset e-mail on a test account → revoke the old key |
| Validate     | The `email.send` job completes (no retries in the worker log); the message arrives with DKIM pass                                                                                                         |
| Rollback     | Old key while it exists; queued jobs retry with backoff (5 attempts) so a short misconfiguration loses nothing                                                                                            |

## 10. `BOOKING_QUOTE_SECRET` (HMAC for signed quote tokens)

| Item         | Detail                                                                                                                                                                                                                        |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Blast radius | Forge a quote token with an arbitrary price for `BOOKING_QUOTE_TTL_MINUTES` (15). The server recomputes the price from stored rates when the booking is created, so the practical impact is limited; still rotate on exposure |
| Generate     | At least 32 random characters: `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`                                                                                                          |
| Overlap      | None; outstanding quote tokens become invalid                                                                                                                                                                                 |
| Order        | Set on the API → redeploy                                                                                                                                                                                                     |
| User impact  | A customer who fetched a quote before the deploy and submits after it gets a validation error and requests a new quote. Harmless                                                                                              |
| Validate     | `GET /vehicles/{idOrSlug}/quote` followed by `POST /bookings` succeeds                                                                                                                                                        |

## 11. `SENTRY_DSN` (error monitoring; optional)

| Item         | Detail                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| Blast radius | A DSN lets anyone send events to the project (noise or quota abuse); it does not grant read access. Rotate on abuse             |
| Generate     | Sentry project settings → Client Keys → create a new key, disable the old (EXTERNAL GATE — NOT EXECUTED; Sentry is not enabled) |
| Order        | Set on the API, worker and the web app's server environment → redeploy → check an event arrives → disable the old key           |
