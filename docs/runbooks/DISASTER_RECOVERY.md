# Runbook: disaster recovery

**Status:** v0.1 (2026-10-17), Phase 10. Audience: the on-call engineer and the founder.
**Production state:** no production environment exists; every vendor step is **EXTERNAL GATE — NOT EXECUTED**. The scenarios are written so they can be rehearsed locally (docker-compose, MinIO, Mailpit, the fake gateway) before go-live.
**Related:** [BACKUP_AND_RESTORE.md](BACKUP_AND_RESTORE.md), [INCIDENT_RESPONSE.md](INCIDENT_RESPONSE.md), [SECRET_ROTATION.md](SECRET_ROTATION.md), [PAYHERE_GO_LIVE.md](PAYHERE_GO_LIVE.md), docs/ARCHITECTURE.md §13, README.md "Database workflow".

## 1. Principles

1. **Forward only.** Migrations are never undone; a bad migration is corrected by a new migration. An application version is rolled back only when the schema it expects is still the schema in the database.
2. **Never over the top.** A restore goes into a new database or branch, is validated, and the application is pointed at it (BACKUP_AND_RESTORE.md §5).
3. **Money first.** Before and after any recovery, the payment anomaly queue (`/admin/payments`) and open `accepted` bookings are checked; every payment attempted during an outage is reconciled.
4. **Degrade, do not improvise.** Each dependency below has a defined degraded mode; no manual "paid", "confirmed" or "refunded" path exists and none may be created during an incident.
5. **Record everything** in the incident log (INCIDENT_RESPONSE.md §10).

## 2. Scenario: database loss or corruption

| Step | Action                                                                                                                                                                                                                                                                                                                    |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | Declare SEV1; scale the API and worker to zero or block traffic at Cloudflare so no new writes land on a broken database                                                                                                                                                                                                  |
| 2    | Choose the restore point (PITR timestamp just before the damage, or the last daily backup). Write it down                                                                                                                                                                                                                 |
| 3    | Restore into a **new** database or branch at the vendor; for a logical dump, `pg_restore` into a new database (BACKUP_AND_RESTORE.md §4 and §5)                                                                                                                                                                           |
| 4    | Validate: row counts for users, provider_profiles, vehicles, bookings, vehicle_holds, payments, payment_events, reviews, audit_events, verification_documents; `select count(*) from drizzle.__drizzle_migrations`; extensions `postgis` and `citext`; `vehicle_holds_no_overlap` present and the overlap query returns 0 |
| 5    | Re-apply anonymisations performed after the restore point (`audit_events` `user.anonymised`) through `POST /admin/users/{id}/anonymise`; re-record refunds recorded after the restore point from portal evidence                                                                                                          |
| 6    | Switch `DATABASE_URL` on the API and worker, deploy, check `GET /api/v1/ready` (`database`, `postgis`, `migrations` all `up`) and the worker log (queues created, schedules registered)                                                                                                                                   |
| 7    | Reconcile payments attempted during the outage (PAYHERE_GO_LIVE.md §6); e-mail users whose bookings changed state in the lost window (they may need to re-request)                                                                                                                                                        |
| 8    | Keep the damaged database read-only for 7 days, then delete; post-incident review                                                                                                                                                                                                                                         |

Data loss between the restore point and the failure cannot be recovered from the platform; the merchant portal (payments) and sent e-mail (Resend logs, 30 days) are the external sources to rebuild what happened.

## 3. Scenario: object storage loss

| Asset                         | Recovery                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vrp-public` photo variants   | Regenerable from the private originals with `processVehiclePhoto` (`apps/api/src/modules/storage/image-processor.ts`). **No rebuild command exists yet**; engineering writes a reviewed one-off script that iterates `vehicle_photos`, reads `storage_key` from `vrp-private`, re-creates the variants under `public_prefix`. Until then, affected listings show broken images and remain searchable only if they still meet `MIN_VEHICLE_PHOTOS` (the count is on rows, not objects) |
| `vrp-private` photo originals | Not recoverable (R2 has no versioning; bucket locks only prevent deletion for their period). Ask providers to re-upload; variants may still exist and keep the listing presentable                                                                                                                                                                                                                                                                                                    |
| `vrp-private` documents       | Not recoverable. The rows stay; streaming fails. Mark each affected document with `POST /admin/documents/{id}/request-replacement` so the provider re-uploads; the `documentsVerified` badge drops only when the row status changes, so consider rejecting the row with a neutral reason if the file is gone for good                                                                                                                                                                 |
| Prevention                    | Bucket lock on `vrp-private` (BACKUP_AND_RESTORE.md §3); storage credentials with object scope only; a periodic copy of `vrp-private` to a second bucket or provider would need a decision record (new infrastructure, CLAUDE.md §2)                                                                                                                                                                                                                                                  |

Rehearsal: locally, delete an object from the MinIO `vrp-public` bucket and confirm the listing still renders with the remaining variants and the API logs the missing object without crashing.

## 4. Scenario: bad migration

Migrations run forward only (`pnpm db:migrate`, advisory-locked, `packages/database/drizzle/*.sql`). A "bad" migration is one that applied but is wrong (wrong default, missing index, data corrected incorrectly) or one that fails midway (each file runs in a transaction, so a failing file leaves the database at the previous migration).

| Step | Action                                                                                                                                                                                                                                                                                          |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | **Stop deploying.** Freeze the pipeline; do not re-run the migration step                                                                                                                                                                                                                       |
| 2    | **Snapshot.** Take a manual backup or branch of the database as it is now (vendor dashboard; `pg_dump` for a logical copy)                                                                                                                                                                      |
| 3    | **Diagnose** with `select * from drizzle.__drizzle_migrations order by created_at desc limit 5;` and the API `/ready` output. A failed file is simply not recorded; a wrong-but-applied file is recorded                                                                                        |
| 4    | **Forward corrective migration.** Write a new migration that fixes the schema or data (never edit an applied file: CLAUDE.md §6), review the SQL (unquote PostGIS types; custom migration for triggers and exclusion constraints), test it on a restored copy of the snapshot first, then apply |
| 5    | **Application version.** Roll the API and worker back to the previous version **only if** that version runs on the current schema (the migration was additive, or the corrective migration restored compatibility). Otherwise ship the fixed application version forward                        |
| 6    | **Restore as the last option.** Only when data was destroyed and cannot be corrected forward: restore the snapshot from step 2 (or PITR) into a new database per §2 and accept the data loss since the snapshot                                                                                 |
| 7    | Verify `/ready` `migrations: up`, run the local test suite against the corrected schema, and record the incident                                                                                                                                                                                |

Note: pg-boss applies its own schema migrations at start (`migrate: true` on both roles); a pg-boss upgrade that fails to migrate blocks both the API and the worker at start. Pin pg-boss upgrades to a release where the API is deployed first and watched.

## 5. Scenario: bad deployment

| Step | Action                                                                                                                                                                                                                                                        |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | Confirm the symptom is the deployment: `GET /api/v1/health` returns the new `version`; `/ready` or the error rate changed at the deploy time                                                                                                                  |
| 2    | If the deployment included a migration, go to §4 first                                                                                                                                                                                                        |
| 3    | Otherwise redeploy the previous Railway deployment for the API, the worker and the web app together (mixed versions can break contracts between web and API)                                                                                                  |
| 4    | Check environment variable changes made with the deploy (Railway variable history); `pnpm production:check` (Phase 10 validator) runs at start and refuses unsafe production settings, so a deploy that never becomes healthy often has a configuration cause |
| 5    | Validate `/ready`, sign-in, a search, a booking request on staging data; check `/admin/payments`                                                                                                                                                              |
| 6    | Railway sends `SIGTERM` to the old deployment with **0 seconds** grace by default (verified 2026-10-17): make sure `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` is set so in-flight requests and pg-boss handlers finish (pg-boss `stop` timeout is 5 s today)       |

## 6. Scenario: lost encryption key (`APP_DATA_ENCRYPTION_KEY`)

| Fact               | Consequence                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| What is encrypted  | Only `user_mfa.secret_ciphertext` (admin TOTP secrets). Nothing else in the database is encrypted with this key (passwords are Argon2id hashes, tokens are SHA-256 hashes, recovery codes are SHA-256 hashes)                                                                                                                                                                                                                                                                                                      |
| If the key is lost | Every admin TOTP secret is unrecoverable. Admins cannot pass the MFA challenge. Recovery codes still verify (hashes), so an admin with recovery codes can sign in once per code                                                                                                                                                                                                                                                                                                                                    |
| Recovery           | 1. Generate a new key and set `APP_DATA_ENCRYPTION_KEY` (SECRET_ROTATION.md §4; no `_PREVIOUS`, the old key is gone). 2. For each admin: `pnpm admin:mfa-reset --email <admin> --reason "Encryption key lost on <date>; re-enrolment required"` (audited `mfa.reset`, signs the admin out everywhere). 3. Each admin signs in with password, is forced to enrol (`ADMIN_MFA_REQUIRED` is on in production), confirms the new factor and stores new recovery codes. 4. `pnpm admin:mfa-report --strict` must exit 0 |
| Prevention         | Keep the key in the password manager with two custodians; Railway sealed variables cannot be read back, so the password manager copy is the only recovery                                                                                                                                                                                                                                                                                                                                                          |

## 7. Scenario: payment gateway unavailable

| Fact                      | Behaviour and action                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Checkout page down        | Customers cannot pay the advance; `accepted` bookings keep their hold until `confirm_by` (24 hours, capped at pickup) and then expire, releasing the vehicle. Nothing is confirmed without a verified notification                                                                                                                                                                               |
| Notifications delayed     | A notification that arrives late but before `confirm_by` confirms the booking normally. One that arrives after expiry is recorded as `late_success` with a refund due (OPERATIONS_RUNBOOK.md §4.4); the customer is e-mailed. PayHere's retry policy is not documented (verified 2026-10-17): reconcile every attempt of the outage window (`POST /admin/payments/{id}/reconcile` or the portal) |
| Action during the outage  | Status note to users; do **not** extend `confirm_by` by editing rows. Where a booking expired because of a prolonged gateway outage and both parties still want it, the customer re-requests and the provider re-accepts (a new hold)                                                                                                                                                            |
| Disable payments entirely | Not possible in production without redeploying: `PAYMENT_GATEWAY` must be `payhere` and `LAUNCH_MODE=production` requires `PAYHERE_ENVIRONMENT=live`. The reversible lever is the Cloudflare maintenance note or scaling the API down; see PAYHERE_GO_LIVE.md §8 for the rollback switches                                                                                                       |

## 8. Scenario: map tiles unavailable

The browser fetches tiles and the style directly from `NEXT_PUBLIC_MAP_STYLE_URL` (OpenFreeMap). If the host is down the map area fails to render; search results, the list view, vehicle pages, booking and payment flows do not depend on tiles (PRD NFR: the list view works without tiles). Action: none required on the server; monitor the vendor; a failover tile provider (MapTiler) would need a decision record (D37, D41) and must not be added during an incident.

## 9. Scenario: e-mail provider unavailable

| Fact                 | Behaviour and action                                                                                                                                                                                                                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Queue behaviour      | `email.send` jobs retry 5 times with exponential backoff starting at 30 s (`QUEUE_DEFINITIONS` in `apps/api/src/jobs/queues.ts`); each attempt may run 60 s; failed jobs stay in the pg-boss tables for 7 days                                                                                              |
| Longer outage        | Jobs that exhaust their retries fail and are **not** re-sent automatically. After the provider recovers, engineering re-queues failed `email.send` jobs from the pg-boss tables (reviewed script; dedupe keys on notifications prevent duplicate in-app rows, e-mails have no dedupe so re-queue once only) |
| User impact          | Verification and password-reset links are delayed (tokens expire after 24 hours and 30 minutes respectively; users can request again). Booking e-mails are delayed but in-app notifications still appear. Deadlines are unaffected (they are stored on the booking)                                         |
| Alternative provider | Any SMTP endpoint works (`SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_REQUIRE_TLS`, `SMTP_USER`, `SMTP_PASS`, `EMAIL_FROM`), but SPF and DKIM for the sending domain must be set up for it first; do not switch during an incident without that                                                           |

## 10. Scenario: hosting region or provider outage

Railway Singapore down: nothing to do but wait and communicate; the database (separate vendor) is unaffected; PayHere notifications sent during the outage are reconciled afterwards (§7). Cloudflare down: the origin is unreachable through the proxied hostname; do not point DNS at the origin directly (TLS and WAF assumptions break); wait. A move to another host is a planned migration, not an incident action (decision record).

## 11. Rehearsal checklist (before go-live)

| Drill                                       | How                                                                                                                                    | Done |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| Local restore drill                         | BACKUP_AND_RESTORE.md §4                                                                                                               |      |
| Worker stop and restart with queued e-mails | Stop `pnpm dev:worker`, trigger a password reset, start the worker, confirm delivery to Mailpit                                        |      |
| Fake gateway late success                   | Let an accepted booking expire locally, then complete the fake payment; confirm `late_success` with refund due and the customer e-mail |      |
| Storage object missing                      | Delete a variant from MinIO; confirm the page renders and the API does not crash                                                       |      |
| Tiles blocked                               | Block `tiles.openfreemap.org` in the browser; confirm the list view and booking flow work                                              |      |
| Encryption key rotation with `_PREVIOUS`    | SECRET_ROTATION.md §4 on a local database with an enrolled admin                                                                       |      |
| Admin MFA reset                             | `pnpm admin:mfa-reset` on a local admin; re-enrol; `pnpm admin:mfa-report --strict`                                                    |      |
| Bad migration forward fix                   | On a disposable local database, apply a deliberately wrong custom migration and correct it with a second one                           |      |
