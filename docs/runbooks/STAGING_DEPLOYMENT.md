# Runbook: staging deployment (go-live Step 1)

**Status:** v0.1 (2026-10-28). Post-Phase-10 go-live **Step 1**. This is not Phase 11 and not a production launch. Everything in the repository that staging needs is prepared and was rehearsed locally in production mode (§12). **No hosting account, database, domain or other external resource has been created.** Every step that needs one is marked **MANUAL ACTION**, and every result that can only be observed on the live platform is marked **STAGING VERIFICATION REQUIRED**.
**Audience:** the founder or operator who clicks through the Railway and Neon dashboards, and the engineer who runs the checks afterwards.
**Related:** [../DEPLOYMENT.md](../DEPLOYMENT.md) (images, release sequence, production), [GO_LIVE_CHECKLIST.md](GO_LIVE_CHECKLIST.md), [SECRET_ROTATION.md](SECRET_ROTATION.md), [BACKUP_AND_RESTORE.md](BACKUP_AND_RESTORE.md), [WAF_AND_EDGE.md](WAF_AND_EDGE.md), [../security/LAUNCH_RISK_REGISTER.md](../security/LAUNCH_RISK_REGISTER.md) (O14–O17), TECH_DECISIONS D10, D68, D73 and D77.

## 4. Topology and names

```text
Internet ──HTTPS──> vehicle-rental-staging-web     (Next.js standalone, :3000, public)
    │                     │ server-side rendering: API_INTERNAL_URL over the private network
    │                     ▼
    └──HTTPS──> vehicle-rental-staging-api         (NestJS, :4000, public; pre-deploy = migrator)
                          │
                          ├──TLS──> vehicle-rental-staging-db   (Neon, Singapore; direct endpoint)
                          │
                vehicle-rental-staging-worker      (NestJS + pg-boss, no port, never public)
                          └──TLS──> vehicle-rental-staging-db
```

| `vehicle-rental-staging-worker` | repo, `RAILWAY_DOCKERFILE_PATH=apps/api/Dockerfile` (same image) | **custom start command** `node dist/worker.js`                                                      | none | **no** (do not generate a domain) | `GET /api/v1/admin/system/worker` (admin + MFA); the image `HEALTHCHECK` is ignored by Railway |

- **Database connection:** use Neon's **direct** connection string (host without `-pooler`) with `sslmode=require` for all three uses: the migrator holds a session advisory lock, and pg-boss in the API and worker relies on session features (D77). Connection counts are small: API ≤ 10 + pg-boss 2, worker pg-boss 4, migrator 1.
- **Private networking:** the web container's server-side calls go to `API_INTERNAL_URL=http://vehicle-rental-staging-api.railway.internal:4000/api/v1`. Browser calls go to the public API URL. The worker needs only the database.
- Railway's `PORT` variable is not read by the API (it reads `API_PORT`), so the generated domain must target port **4000** explicitly. On the web service set `PORT=3000` explicitly and target **3000**.

### 5.3 Generating the staging secrets

Generate them on the operator's machine, never in chat or in a shared document, and paste each straight into a Sealed Railway variable. Keep a copy in the password manager under "vehicle-rental **staging**". They must not be reused from local development, from the test suites or later from production.

```bash
# Ed25519 pair as one-line PEMs with \n escapes, printed to this terminal only (copy each
# value into its Sealed variable, then clear the terminal; never redirect it into the repository)
pnpm --filter @vrp/api keys:generate
# APP_DATA_ENCRYPTION_KEY (32 bytes, base64)
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
# BOOKING_QUOTE_SECRET (32 bytes, hex)
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Delete any file that held a secret once the value is stored in Railway and in the password manager.

### M3 — Railway project and services

1. Open `railway.com/dashboard` → **New Project** → **Empty Project**. Rename it `vehicle-rental-staging` (Project → Settings). If Railway asks for a plan, choose the one approved in M1.
2. In the project's environment (Railway calls it `production` by default), rename the environment to **staging** (Project → Settings → Environments) so logs and variables never suggest production.
3. **+ Create → GitHub Repo** → authorise only the `vehicle-rental-platform` repository → branch `main`. Rename the service to `vehicle-rental-staging-api`. Repeat twice for `vehicle-rental-staging-worker` and `vehicle-rental-staging-web`.
4. For **each** service, open **Settings**:
   - **Deploy → Regions:** Southeast Asia (Singapore).
   - **Deploy → Restart policy:** On failure.
   - `api`: **Deploy → Pre-deploy command** `node node_modules/@vrp/database/dist/migrate.js`; **Healthcheck path** `/api/v1/ready`; health-check timeout 60 s.
   - `worker`: **Deploy → Custom start command** `node dist/worker.js`. Leave the health-check path empty.
   - `web`: **Healthcheck path** `/`.
   - **Source → Wait for CI:** on (deploy only after the GitHub CI checks pass). Railway deploys `main` automatically; this deploys to **staging only**, and nothing in this project is production.
5. **Variables:** first open **Project → Shared Variables** and add the variables marked ✓ for both API and worker in §5.1, sealing each secret. Then, in each service's **Variables** tab, reference the shared ones and add the service-only ones (`RAILWAY_DOCKERFILE_PATH`, `RAILWAY_DEPLOYMENT_DRAINING_SECONDS=15`; API: `TRUST_PROXY_HOPS=1`; web: everything in §5.2). Use **Raw Editor** only for non-secret values.

8. **Reply with:** each service's deployment status (Active / Failed / Crashed), the generated public hostnames of web and API, the private hostname of the API (`…railway.internal`), and the first error line of any failed deployment. Do **not** copy variable values or the `DATABASE_URL`.

Until B1 is resolved the API and worker deployments **will fail at start-up** with `Invalid environment configuration` listing the B1 variables. That is the schema working as designed, not an error to work around.

### M4 — Reference data (once, after the first successful API deploy)

The seed is reference data only (districts, places, categories, platform settings) and is idempotent. Railway has no one-off job runner in the dashboard, so for this single run add it to the API pre-deploy command, `sh -c "node node_modules/@vrp/database/dist/migrate.js && node node_modules/@vrp/database/dist/seed/index.js"`, redeploy, then restore the migrate-only command. Alternatively run it with the Railway CLI (`railway ssh` into the API service), if the operator installs it later.

## 7. Release sequence on staging (every deploy)

`build` (Railway, per service) → **api pre-deploy: migrate once** (advisory lock; forward-only; a failure stops the rollout and the previous API keeps serving) → api becomes active when `/api/v1/ready` answers 2xx → `worker` → `web` → `pnpm smoke:staging` (§11). No service migrates on start-up; the worker never migrates.

## 8. Health and readiness

- `GET /api/v1/health` answers `{status, service, version, environment, uptimeSeconds, timestamp}` and never touches the database. It carries no URL, credential or stack trace.
- `GET /api/v1/ready` answers 200 only when `select 1`, the PostGIS extension and at least one applied migration all succeed (3-second timeout each); otherwise **503** with per-check status and a fixed generic message (`database unavailable`, `PostGIS unavailable`, `migration check unavailable`). The driver error (host, address, port) goes only to the server log as `Readiness check failed` with the connection URL redacted. Railway's health check uses it, so a database outage takes the API out of rotation while `/health` stays 200.
- The release identifier is `APP_RELEASE`, attached to every log line and error event. `/health.version` is the package version (`0.1.0`), not the commit, so check the release in the logs.

## 9. Trusted proxy (STAGING VERIFICATION REQUIRED)

With `TRUST_PROXY_HOPS=1`, Express takes the last `X-Forwarded-For` entry, and when that header is absent `app.setup.ts` copies Railway's `X-Real-IP` into it. Railway does not document whether its edge appends to, replaces or forwards a client-supplied `X-Forwarded-For`. If it forwards the header unchanged, a client could choose its own rate-limit key. **Before testers are invited**, run `pnpm smoke:staging`. Step 17 sends spoofed `X-Forwarded-For` and `X-Real-IP` after reaching the login limit and must still receive `429`. If it fails, stop and record it in the risk register (O15); the fix is a small change to the shim (prefer the edge's `X-Real-IP` when hops > 0), made as its own reviewed change. Never set `TRUST_PROXY_HOPS` higher than the real number of proxies.

## 10. Admin and test accounts

- Staging admins are created only with the official path: the person registers on the staging web app with a dedicated staging address, verifies it through the e-mailed link (needs B1), then `admin:grant` runs from the API image against the staging database, for example as a one-off pre-deploy command `node dist/cli/grant-admin.js --email <staging address> --role super_admin`, restored afterwards. No manual role inserts, no shared TOTP secret, no production admin addresses.
- On first sign-in the console forces TOTP enrolment (`ADMIN_MFA_REQUIRED=true`). The tester enrols their own authenticator and keeps the recovery codes in the password manager under the staging entry.
- Customer and provider test accounts use addresses and names that start with `staging-` (for example `staging-customer-01@…`, provider business name `STAGING TEST DATA — …`). Listings created on staging are titled `STAGING TEST DATA — …` so they can never be mistaken for real supply. Staging data is never copied to production, and production data is never copied to staging.

## 11. Staging smoke (`pnpm smoke:staging`)

```bash
SMOKE_WEB_URL=https://<staging web> SMOKE_API_URL=https://<staging api>/api/v1 pnpm smoke:staging
# optional worker check: an MFA-completed admin access token in the environment (never printed)
SMOKE_ADMIN_ACCESS_TOKEN=… SMOKE_WEB_URL=… SMOKE_API_URL=… pnpm smoke:staging
```

`scripts/smoke-staging.mjs` sends HTTP requests only. It creates no accounts, data, bookings or payments and calls no third party. Its 18 steps cover HTTPS; `/health` fields and environment; `/ready`; API headers (CSP `default-src 'none'`, HSTS ≥ 1 year with `includeSubDomains`, nosniff, frame deny, no-referrer, COOP, no `X-Powered-By`); CORS for the exact web origin with credentials; refusal of hostile, `null` and suffix-trick origins plus a hostile-origin refresh (403); Swagger and the fake gateway unmounted (404); 401 on protected routes; 400 on malformed and invalid bodies; 413 on a 300 KiB body; home with the nonce + `strict-dynamic` CSP, the API in `connect-src`, no wildcard and HSTS; search, login, register and become-a-provider pages; legal drafts withheld (404); the MapLibre worker at `/maplibre/` with `worker-src 'self' blob:`; no `/.git` or `/.env`; the worker status with all four schedules (optional); the login limiter not reset by spoofed forwarding headers; and no 5xx. It prints a random canary that it sends as a bearer token and inside a password. Search the Railway logs of `api` for it afterwards: it must not appear. The limiter step uses up the runner's login budget for a minute, so run the smoke at most once a minute.

Not covered by the smoke, check by hand in a browser on staging: no CSP violations in the console on `/`, `/search`, a vehicle page and `/login`; the map renders, or the list still works with the tile host blocked; sign-in, refresh after reload, logout and logout-all (needs B2); admin MFA enrolment (needs B1 + B2).

## 13. Rollback

- **Application:** Railway → service → **Deployments** → previous successful deployment → **Redeploy** (api, then worker, then web). Allowed while the schema stays compatible; migrations are additive (expand / contract).
- **Database:** never down-migrate and never delete the database. On a schema problem: stop the rollout (do not deploy worker or web), redeploy the previous API only if it runs on the new schema, otherwise write a forward corrective migration and deploy it through the same pre-deploy step. Neon's restore history (6 hours on Free) is the last resort for staging and discards writes made since.
- **Configuration:** a wrong variable makes the new deployment fail its health check, and the previous one keeps serving. Fix the variable and redeploy.

## 14. Backups (staging)

Neon keeps restore history (Free: 6 hours; Launch: longer, priced per GB-month) and can restore a branch to a point in time from the console. Record what the console shows at M2. No restore is performed against staging in Step 1. A restore drill into a separate branch can be planned later (BACKUP_AND_RESTORE.md §5).

## 15. Tearing staging down later

1. Railway: project `vehicle-rental-staging` → Settings → **Delete project** (removes the three services, their variables and domains). Check that the project name contains `staging` before confirming.
2. Neon: project `vehicle-rental-staging-db` → Settings → **Delete project**.
3. Revoke the staging-only credentials: Resend key, R2 token, PayHere sandbox app (Step 2 items), the GitHub app access granted to Railway if no longer needed.
4. Delete the staging entries in the password manager once nothing references them.

Never delete anything whose name does not contain `staging`.
