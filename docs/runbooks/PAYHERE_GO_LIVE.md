## 1. What the integration does (so the checklist makes sense)

- `POST /bookings/{id}/payments/checkout` builds a hosted-checkout form for the advance (`bookings.advance_amount`, two decimals, LKR) with `hash = UPPER(md5(merchant_id + order_id + amount + currency + UPPER(md5(merchant_secret))))`, computed server-side only.
- PayHere posts the result to `PAYHERE_NOTIFY_URL` (`POST /api/v1/payments/payhere/notify`, `@Public()`), which verifies `md5sig = UPPER(md5(merchant_id + order_id + payhere_amount + payhere_currency + status_code + UPPER(md5(merchant_secret))))` timing-safely over the received strings before any write, always answers `200`, treats `(gateway, gateway_payment_id)` as unique, never downgrades a verified success, and records a late or duplicate success as `paid` with an anomaly and a refund due. Status codes: `2` success, `0` pending, `-1` cancelled, `-2` failed, `-3` chargedback.
- `return_url` / `cancel_url` point at `/bookings/[id]/payment`, which polls the booking; the URL is never trusted.
- Merchant API (optional): `POST /admin/payments/{id}/reconcile` (Retrieval by `order_id`) and refund mode `gateway` (`POST /admin/payments/{id}/refund`) work only when `PAYHERE_APP_ID` / `PAYHERE_APP_SECRET` are set; otherwise they answer `503` and refunds are recorded manually.
- Card data never touches the platform (hosted checkout). Notifications carry masked card fields; the platform does not store or log them.

## 6. Reconciliation routine (daily during validation)

1. `/admin/payments`: resolve every `requires_manual_resolution` row (OPERATIONS_RUNBOOK.md §4).
2. Compare the merchant portal's payment list for the day with `GET /admin/payments` (status `paid`) by `order_id`. PayHere's retry behaviour for notifications is **not documented**, so a payment in the portal without a `paid` row is possible after an API outage: `POST /admin/payments/{id}/reconcile` when the Merchant API is configured, otherwise treat as the portal says and follow OPERATIONS_RUNBOOK.md §4 (if the booking has expired meanwhile, it is a late success handled by refund, never a manual confirmation).
3. Check `accepted` bookings close to `confirm_by` with a pending attempt and a portal success: same procedure.
4. Record refunds processed in the portal that are not yet recorded.

## 7. Refunds: facts and the open conflict

- Refund API (`POST /merchant/v1/payment/refund`) accepts `payment_id`, `description` and an `amount` "used for partial refunds"; the Refund Process page states "PayHere supports only full refunds" and that partial amounts must be returned manually. **Conflicting documentation: confirm with PayHere in writing before relying on partial refunds.** The platform's policy is full refund or forfeited, so no partial refund is needed today; the admin refund endpoint accepts partial amounts only as a record of what was done outside.
- Same-day refund (before the day-end payout) is an instant void; after payout, 5 to 10 days or longer. PayHere states it refunds the processing fee to the customer as well.
- Frimi, Genie, eZcash, mCash and Vishwa payments cannot be refunded through PayHere: bank transfer, recorded with mode `manual`.
- Nothing is ever marked refunded automatically; the admin records every refund (D56).

## 8. Rollback and disabling payments

| Situation                                            | Action                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Live payments must stop (fraud, wrong configuration) | Production cannot run the fake or sandbox gateway (`LAUNCH_MODE=production` requires `PAYHERE_ENVIRONMENT=live` and `PAYMENT_GATEWAY=payhere`). To stop payments: redeploy the API with `LAUNCH_MODE=staging` and `PAYHERE_ENVIRONMENT=sandbox` (checkouts then go to the sandbox host and no real money moves; the sandbox merchant credentials must be set), or scale the API down behind a maintenance note. **The worker is untouched** in both cases (it does not call PayHere) |
| Wrong Merchant Secret after rotation                 | SECRET_ROTATION.md §5: set the correct secret, redeploy, reconcile the window                                                                                                                                                                                                                                                                                                                                                                                                        |
| Merchant API misbehaving                             | Unset `PAYHERE_APP_ID` / `PAYHERE_APP_SECRET` and redeploy: reconcile and gateway refunds answer `503`, manual recording continues                                                                                                                                                                                                                                                                                                                                                   |
| Return to live after a stop                          | Reverse the variables, redeploy, run the first-live-payment checklist (section 5) items 1, 5, 6 and 7                                                                                                                                                                                                                                                                                                                                                                                |

In every case `accepted` bookings whose customers could not pay expire at `confirm_by` and release the vehicle; do not extend timers by hand (INCIDENT_RESPONSE.md §7).
